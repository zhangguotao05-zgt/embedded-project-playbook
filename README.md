# AI 协作开发管理

独立维护项目开发方法、角色分工、交付流程和验收规则的私有文档仓库。基础协作手册版本为 **v1.6**，通用软件系统开发手册版本为 **v1.0**。

## 阅读方式

- 主文档：[AI 协作项目开发手册](index.html)。
- App / Web / PC / API：[通用软件系统开发手册 v1.0](software-development.html)，覆盖模块架构、开发与生产配置、完整功能交付、增量验收、发布回滚及维护。
- 新软件项目：[可复制的项目执行约定](templates/software-project.md)；已有项目保留当前结构与入口，填写实际采用范围后生效。
- 直接使用：[Issue 过程记录与评论模板](index.html#issue-log)、[增量验收规则](index.html#incremental-review)。
- 固定职责：[正式角色与内部辅助的边界](index.html#role-contract)、[长任务恢复检查](index.html#role-recovery)。
- 代码质量：[Q1–Q6 自检与独立验收](index.html#code-quality)，在现有交接中记录依据，不另建审批链。
- 日常操作：[已验收固件的普通烧录](index.html#routine-flashing)，烧录 → 完整回读 → 基本启动验证，保留原始日志与一份操作记录。
- [GitHub 工作包表单](templates/github-work-package.yml)是可复制模板；没有自动安装到任何产品仓库，不需要为已有功能重复创建 Issue。
- GitHub 仓库保存源文件，不直接呈现完整 HTML 页面。克隆或下载本仓库后，在浏览器打开根目录的 `index.html` 或 `software-development.html`，即可阅读完整排版；无需安装依赖。
- 本仓库保持私有，未启用 GitHub Pages 或其他公开网页托管。

## 手册内容

- 需求分析、范围确认与验收标准。
- P 产品与需求、A 架构与交付、B UI/UX、C 软件/固件、D 独立测试五个基础角色。
- 按需增加 E 应用工程师；自研电路或 PCB 时安排 H 硬件工程师。
- 软硬件交接、独立审查、样板实测和风险分级。
- 开发流程、任务卡、六类记录、并行规则及可复用角色说明。
- L0/L1/L2 分级、证据复用条件、按需专业复核、版本生效和角色确认。
- 一项完整功能一个 Issue：记录关键开发步骤、送审、整改与独立结论，原始证据只存一份。
- 正式角色按登记任务交接；内部助手不得代签，署名更正保留证据；恢复时读取职责与当前记录，不重复搭环境或无依据重建。
- 职责、接口、所有权、恢复、简洁和跨模块测试六项检查；明确未审不算通过、自动检查边界和技术债处理方式。
- 普通烧录沿用已验收镜像与现有工具，不重复软件审查、输入复制或报告封存；遇到实际变化和失败再补受影响检查。
- 通用软件手册补充 App、官网、PC 和后端的职责边界、接口与数据、环境配置、平台生命周期、CI/发布、隐私与恢复；附 Flutter＋后端、静态官网、Electron 三类实施示例。
- 开发、联调和生产使用统一配置入口；本地测试路径推动独立开发，真实认证、外部集成和发布条件分别验收。

## 维护规则

1. 核心协作规则只在 `index.html` 中维护；软件项目实施细则在 `software-development.html` 中维护并引用核心规则，避免复制后漂移。README 仅保留入口和摘要，`templates/` 提供可复用表单。具体项目的执行约定、角色入口和同步回执保留在各自项目的本地受控记录中，不默认上传本仓库。
2. 涉及角色、流程或验收规则的修改，同步相关章节及版本标记。
3. 提交前检查本地链接、章节锚点和浏览器显示。
4. 不存放产品源码、设备日志、受限设计素材、密钥或账号凭据；具体项目的实施证据由各自项目管理。
5. 本仓库中的流程模板不构成刷写、采购、制板、公开发布或其他外部操作的授权。
6. 规则应用到具体项目时，按已有授权向现有角色发送版本与生效范围，记录实际回执；不能只推送文档就宣称角色已采用。新增手册不会自动改变现有项目或正在运行的验收任务。

本仓库为内部使用资料，不因存储于 GitHub 而获得公开分发授权。
