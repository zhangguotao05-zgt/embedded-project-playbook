让嵌入式完整功能持续交付

从想法起步、需求尚未冻结的界面与嵌入式项目，软件与界面部分推荐 5 个核心 AI 角色＋1 位人类产品决策者；自研电路或 PCB 时另设 H：硬件工程师。需求分析有明确负责人；先把一个代表性功能从需求做到设备上，再扩展。

2026-10-08 · 协作规则 v1.6 · 假设：你负责产品决策，项目包含界面与嵌入式软件，可使用现成开发板或设计自己的硬件。角色数是配置建议，不是固定人数；硬件实测、电气安全及专业审查需要具备相应能力的人员承担。

使用顺序：启动时先确认目标与范围、分配职责、约定验收和操作权限；再完成代表性设计与技术验证，交付首个端到端样板；之后按工作包滚动开发、独立验收并维护统一记录。

日常执行：普通工作包由 C 自测后直接交 D；A 处理技术边界，B 处理新设计或视觉争议，H 处理硬件变化，不设置逐角色串行签字。一个工作包、一条 Issue 主线、一份候选证据入口。

直接使用：代码质量六项检查 · 固定角色、辅助意见与恢复检查 · 过程记录方法与评论模板 · 可复制的 GitHub Issue 表单。

职责、AI 任务和同时运行数是三个概念。一个角色可以兼任相容职责；五个固定角色也不要求五个任务始终并发。你最终决定价值、范围和风险，不需要自己完成专业需求分析才交给团队。

日常统一汇报仍由 A 负责。P 管理需求与优先级建议，A 管理交付依赖和技术风险；你可直接回答 P 的需求问题，但不需要在角色间反复转述。需求角色不会给所有改动额外增加一道审批。

  • 精简配置：4 个 AI，把 P 的需求分析与 A 的架构/交付合并，其余为设计、工程、独立验证。适合用户和需求已清楚的小项目；需求产物及确认步骤仍必须存在，自研硬件仍须另设 H。
  • 推荐配置：软件与界面采用 5 个核心角色，独立设置 P：产品经理兼需求分析师。适合从模糊想法开始、产品流程较多的项目；P 与 B 前期投入较大，后期维护需求变更和下一批设计。
  • 需要并行开发：按需增加 E：应用/业务工程师，前提是接口稳定、工作目录隔离、确有互不依赖的模块。共享路由或同一驱动还没有理顺时，增加人数通常先增加合并成本。
  • 自研电路或 PCB：从需求阶段增加 H：硬件工程师，即推荐配置的 5 个基础角色＋H；同时增加 E 时为 7 个责任角色。H 可由硬件专业人员担任，并用 AI 辅助设计与审查，不能用增加一个 AI 代替实际测量与人类硬件责任。
  • 仅使用现成开发板：可暂不设常驻 H，由 C 负责接口适配；遇到电气问题安排硬件专业支持。涉及结构、量产及认证时，另分配对应专业职责，不默认由 H 一人包办。

角色数量不等于加速倍数。设计、实现、集成、板测中最慢且不能并行的一段决定整体节奏；先减少等待与返工，再决定是否增加角色。

2. 谁负责什么，谁不能自己签字

角色人数主要责任与固定交付权限边界

C：主软件/固件工程师兼集成人1 个拥有端到端工作包；实现页面到服务的完整链路，维护构建、驱动边界、基础自测与诊断；产出候选版本。在批准范围内自主实现和修复；共享接口、高风险硬件变更、公开推送和刷写需遵守明确授权。
D：独立测试与质量工程师1 个开发前补验收案例，开发中维护自动化，开发后检查代码、截图、故障路径及绑定版本的实机证据；自研硬件时组织独立专业审查与实测核验。不能仅复述开发者的“通过”，不替代自己不具备能力的专业审查。若亲自修了生产逻辑或硬件设计，该改动交其他未参与实现者复核。
E：应用/业务工程师，可选增加 1 个在稳定接口上实现独立业务，例如计时器、设置、内容浏览；由 C 集成。不得与 C 同时改共享路由、资源目录和同一工作树；所有权冲突先协调。
H：硬件工程师，自研硬件必设增加 1 个责任角色从需求阶段参与器件、电源与接口方案；交付原理图、PCB、BOM、软硬件接口表、制板资料及样板测试记录；与 C 联合调试。不是自己设计、自己最终验收。设计须独立专业审查；采购、制板和台架操作需明确授权，电气安全与实测由具备能力的人员负责。

三种管理职责区分：P 管“为什么做、做什么、先做什么”，A 管“系统怎么组织、如何按依赖交付”，你作最终产品决策。小团队不再单设日程协调员、文档员或发布员；相应职责必须按下表分配。

“不单独安排一个 AI”不等于“不做这项工作”。是否新增角色，要看专业风险、持续工作量和并行价值，而不是为了让名单看起来完整。

H：硬件工程师从什么时候加入，完成后交给谁

自研电路或 PCB 时，H 从需求阶段加入。P 明确产品目标，H 确认器件、功耗、成本和电气可行性，C 确认驱动与软件支持，A 协调系统边界，D 提前定义可测的验收条件。只使用现成开发板时，可按需安排 H 支持，不给普通页面开发增加硬件审批。

硬件完成后的验收流程

  1. H 自检后交给 D：提交硬件资料版本、自检结果、接口契约、已知问题和本次申请的验收范围；D 是验收协调入口。
  2. 制板前先审设计：D 组织独立硬件专业审查，A/C 核对系统接口；H 修正问题，由独立审查者复验。设计通过后，仍须获得明确的采购/制板授权才能向供应商交付。
  3. 样板到手再做实测：具备能力的人员按授权操作台架，H 与 C 联合调试；D 核对板号、硬件版本、匹配固件、仪器/条件和原始结果，按风险安排独立复测。
  4. D 汇总验收结论：设计审查与样板实测分别记录通过、失败或待验；不把“图纸通过”“板能启动”写成硬件全部通过。未解决问题明确负责人、影响和关闭条件，里程碑由 A 汇总并由你决定范围与风险接受。

H 不能作为自己设计的唯一验收者。D 若不具备硬件专业能力，就负责组织和核验证据，不代替专业人员判断；独立硬件审查者可按阶段安排，不必常驻。AI 辅助检查不能代替电气安全责任、实物测量或适用认证。

交接示例：蜂窝页面完成后由 C 直接交 D；D 按已批准设计检查视觉，仅在新设计、重大偏差或争议时找 B。仅改布局、图标不要求 H 签字。新增屏幕电路、调整供电或触摸接口时，H 负责硬件、C 负责驱动，D 组织软硬件联合验收，A 复核系统影响。

3. 开发流程：五个阶段，三个业务关口

  1. ① 需求分析与范围目标、用户、场景、规则、验收
  2. ② 设计与可行性并行主流程、资源与最大风险
  3. ③ 做一个完整样板真实页面 → 服务 → 设备
  4. ④ 滚动交付沿用样板，成组接入
  5. ⑤ 冻结、验收与维护版本、证据、风险、反馈

需求分析由 P 主责，架构师参与，不由架构师单独包办

P 把“我想要一个什么产品”变为“哪些人在什么场景遇到什么问题、系统应如何响应、什么结果算成功”。A 检查技术约束和系统影响，B 检查流程与体验，D 检查能否验证，C 提供实现成本；你确认实际意图和取舍。

  1. 发现与澄清：收集你的目标、真实使用场景、参考产品、现有痛点和预算。区分已确认事实、假设与未知，问题分组询问，不让你先自己写一份完整需求书。
  2. 分析与拆分：列出用户流程、功能、状态、业务规则和外部依赖；同时覆盖性能、可靠性、功耗、内存、隐私、升级与可维护性等适用的非功能需求。
  3. 范围与优先级：划分第一版必需、后续、仅演示及明确不做的内容。对冲突给出方案与代价，由你决定；技术未知先做小型验证，再承诺指标。
  4. 可验证化：每条关键需求有稳定编号、前置条件、输入/动作、预期结果、异常边界及验证方式；性能数值要注明测量环境，未定阈值明确标记，不能伪造精度。
  5. 联合确认：P/A/B/D 审核遗漏、矛盾、可行性和可测性，C 估软件成本，自研硬件时 H 核对电气可行性和硬件成本；你确认基线。在同一轮解决关键冲突，不要求所有角色依次给每个细节盖章。
  6. 持续管理：每个新批次补齐对应细节；需求变更记录原因、收益及对设计/代码/测试/排期的影响。冻结的是本批承诺，不要求开工前把多年路线图细化完。

最低交付：一页目标与范围、带编号的需求台账、核心用户流程、验收标准、未知/假设清单。它们可放在同一份记录中，建立 需求 → 页面/接口 → 工作包 → 测试 → 候选证据 的链接，不另起重复文档。

示例：把“尽量复刻 Apple Watch”变成能开工的需求
  • 参考哪个系统版本、哪几条核心流程？按特定参考复刻，还是接受项目适配？
  • 哪些功能必须真实可用，哪些仅演示，哪些没有硬件/服务而保持不可用？
  • 图标、布局、字体、动效各接受什么偏差？用哪份批准图和哪种目标渲染结果比较？
  • 锁定、返回、切页、掉电和失败时怎样响应？只画页面不能替代这些行为定义。
  • 以“水锁”为例，需求明确触摸与普通按键的阻断范围、解锁动作、松手条件、返回目标和异常行为；架构才决定输入仲裁与状态机怎样实现，测试据此验证。
  • 素材能否按预期方式交付，硬件和内存是否支持？这些是第一版承诺的前提，不留到最后才决定。

关口 G1：第一版究竟交付什么

P 汇总“目标用户、3–5 条首要用户流程、不做什么、硬件/服务条件、核心体验与可靠性指标”，A/C 核对可行性；自研硬件时 H 同时评估器件、电源、成本和制板风险，D 检查验收可执行性。你批准优先级和边界；未确定的功能进入待办，不一开始铺开所有页面的实现承诺。

关口 G2：样板证明设计能够落地

B 做代表性核心页面与组件，C 并行验证最难的工程部分，D 同时准备验收。选 1 条完整流程，并让它覆盖本项目最关键的风险：例如大字号、透明图片、滚动、服务回执、取消/返回和一次失败回退。需要额外覆盖的渲染类型可再选 1–2 页。

自研硬件时，H 并行完成设计审查与样板计划，C 可在已确认接口的开发板上推进软件。开发板结果只证明该平台；产品板到手后由 H/C 联调、D 组织补验，不能直接继承开发板的电气、功耗或时序结论。

  • 用最终计划采用的字体、图片转换、目标工具链和绘制路径，不把浏览器视觉稿等同于固件样板。
  • 量出真实资源和性能开销，确认素材许可与替代路线；不要等做完几十页后才发现预算不成立。
  • 硬件不可用时，最多批准到主机或目标构建范围；明确实机退出条件，不把这一项写成已通过。
  • 你确认关键体验，A 确认架构与预算，D 核验证据。之后相同设计系统不再反复审批。

常规开发：整包审查，不再每个中间产物排队

每批通常是 1–3 个相关完整页面或一条用户流程；复杂功能只做 1 个也可以。内部任务、提交、测试可以很细，外部交付必须能操作、能返回、能处理失败。继续按风险做代码审查，不为每张字体样张新增业务关口。

C 实现与自测 → D 独立检查 → C 修正阻断 → D 增量复核。先做最小冒烟和需求/截图核对，明显缺项及时反馈，不等长测或完整报告写完才通知；发现崩溃、内存破坏等问题须保留首个失败证据。非阻断改进集中入待办，不顺手扩展为重构、换工具或更换设计方向。

关口 G3：里程碑/版本验收

冻结候选，D 输出与该候选绑定的检查结果，P 核对承诺的用户需求，A 汇总交付情况及未关闭风险，由你确认范围和是否允许发布。发布后 P 收集反馈，C/D 维护和回归，A 管兼容及升级风险。日常演示、阶段通过、版本发布是不同决定；每个小批不需要重走全部立项流程。

高风险变更可随时触发专门审批，例如分区/引导/持久化兼容、电源和时钟、DMA/缓存所有权、升级安全或扩大远端权限。“三个关口”不是豁免这些风险，也不会覆盖原有更严格的项目要求。

4. 怎样并行，才真正减少等待

同一阶段当前工作下一份交付
P：需求澄清下一批价值、范围、规则和验收；处理变更输入齐全、优先级明确的需求与任务
B：设计下一批 N＋1 的规格与状态；支持当前批问题可直接实现的设计包
C：实现当前批 N 的完整功能；优先修复已确认阻断可操作候选＋最小自测
H：硬件，适用时按板卡阶段完成设计、独立审查整改、样板调试；提前稳定与 C 的接口带版本的硬件资料、接口契约、实测证据及适用限制
D：验证上一批 N－1 的验收，以及 N 的提前测试准备一次性、按严重度排序的结论
A：交付管理协调依赖、共享改动、风险和待决定事项一份当前看板与必要决策请求

这是进入稳定节奏后的流水作业，第一批仍有依赖，不能假装全部可以并行。设计通常领先实现一个批次即可；先掌握系统结构和高风险页面，再逐批补齐细节。

限制同时在做的工作

  • 单个工程师同时负责 1 个主要实现包；增加 E 后，整个团队最多先试行 2 个并行实现包。
  • 待审核队列默认不超过 1 个批次。出现积压，先帮助验收和修复，不继续制造更多“开发完成、等待确认”。
  • 一块开发板同一时刻只有 1 个执行者；串口、烧录、复位及测试电源不能由两个任务同时控制。
  • 设计师一次交一个完整包；验证者一次汇总已知问题，避免一天只抛一个小改动。新出现的真实缺陷仍可以新增，不能为了“一轮审查”压住问题。

文件、分支、环境与设备隔离

环境由 C 维护，D 独立验证：复测入口应带齐源码、测试夹具、配置、测试所需文档/补丁清单及资源定位；运行前快速核对指纹和依赖。环境不变时复用已验证环境，不复用陈旧测试结论；环境改变时重新预检。Windows 使用已验证的短路径。优先封装现有命令，不另造一套平行测试框架。

环境问题默认以约 10–15 分钟为首次反馈检查点，说明失败命令、已证实原因和可继续的检查；这是反馈点，不是自动跳过或通过的期限。只对已识别的瞬态问题有限重试，不重复运行未修复的相同失败，也不由 D 静默改生产代码或降低门禁。

  • 并行代码任务使用独立分支和工作目录。共享模块明确负责人，其他任务先提出接口需求，不能直接覆盖正在修改的文件。
  • 只由 C 合并并产出软件送测候选；H 维护硬件设计主文件并冻结制板资料，其他角色不得同时覆盖同一 CAD 工程。D 在只读候选或隔离目录复测，不能覆盖工程师原日志、截图和输出。
  • 固定 SDK、工具链与依赖；补丁使用清单管理，保留干净基础 SDK。提前提供“一次命令复测”的入口，避免每轮重装环境。
  • 使用小型本地提交或私有仓库保存进度。受限素材留在受控位置；内部保存不等于允许公开推送。
  • 设备登记至少包含板号、硬件版本、固件身份、当前操作者、执行项目与释放状态。H、C、D 共用设备时遵守同一占用规则，每次换人或换候选先确认。

已验收固件的普通烧录可直接在既有任务记录中写明候选、目标、授权范围和结果，不为同一操作另建完整开发任务卡或重复 Issue。

什么时候算“可以开工”

有明确用户行为、设计与接口输入、可执行验收标准、负责人和依赖。缺少决定性输入时，先列为“探索任务”：限时回答一个具体问题，不伪装为实现已经进行到 90%。

什么时候算“完成”

工作包声明的正常、取消/返回、失败路径已闭环；相应风险测试完成；目标资源在预算内；要求实机的行为有实机证据；独立验证通过；状态和剩余问题已经记录。只完成静态图、编译、日志整理或主机样片，应使用相应阶段名称。

允许部分验收，但不允许模糊完成：例如“主机视觉通过，板测待验”是合法状态，不能计为“目标设备功能完成”。决定延期的条目仍保留，不通过删除条目抬高进度。

可执行的交接门槛：C 的自检缺候选、范围或依据，交接保持“待补充”；D 没审代码则代码质量保持“未审”，可以继续其他检查但不能给整包“已验收”。D 给出独立结论，不复制 C 的勾选。一个测试结果不能替代全部六项；已审证据可以链接复用，不重复抄写。

机器与判断分工：沿用项目已有格式、编译警告、静态分析、明确依赖边界和相关回归入口。记录本轮执行、适用复用、未执行或阻断；不新增无依据的全量双构建。新诊断须处置，已确认缺陷及明确架构边界违规先修；历史告警、误报、函数长度或复杂度提示结合影响判断，不把指标直接当质量分数。工具不能自动证明高内聚、低耦合。

  • 阻断：可触发崩溃、触摸穿透、数据损坏、关键流程失效、越预算、镜像身份不一致、无授权高风险操作，或当前交付必需证据缺失。给出触发、影响、最小修正和验证方法。

适用条件：使用已有独立软件验收记录的确认镜像，本次不修改源码或构建输入；镜像与验收记录一致，目标及现有布局已确认兼容，沿用已验证的烧录工具、备份与恢复方法。操作须在用户已授权范围内；范围未变时不重复请求同一许可。

扩大检查的条件：出现未验证的源码、构建、镜像/描述符、目标、工具、布局、引导、保护或安全相关变化，兼容性不明、证据缺失、写入/回读失败或启动异常时，停止受影响步骤，检查实际差异和失败原因，补必要验证后再继续。失败未处理时不重复相同尝试；超出许可范围的操作另获授权。

返工退回原因：需求变更、设计缺失、实现缺陷、环境、证据不齐区分需求变化与工程质量，不把所有慢都算在开发者身上
漏检与稳定性已验收功能的新回归缺陷、关键测试不稳定、实际故障次数加速同时监控质量，避免只奖励速度

建议探索任务先约定半天到一天的检查点：到点交“证实/证伪/还缺什么”，必要时重新估时，不能静默扩展。连续两轮视觉微调没有形成新决定时，由 B＋你一次确定接受范围；待验队列超过一个批次时，A 先清理阻断，不继续堆积新实现。

每批只增加几个可自动获取的时间字段：开始、首次可操作、送审、首个反馈、验收；环境修复、机器执行、人工/AI 审查、外部等待分开看，避免把整段对话时长当作编译或测试耗时。前两批只校准，不承诺固定加速倍数；若漏检、返工或不稳定上升，扩大对应检查。

汇报只用五行：本批交付了什么；可点开的演示/候选在哪里；主机/构建/实机各是什么状态；真正的阻断是什么；下一批做什么。没有变化不重复长篇汇报，但不能隐藏失败或不确定性。

9. 核心与硬件角色的可复用任务说明

下列说明配合当前任务卡和六类记录使用。每次任务都给范围、输入版本、允许修改位置、验收标准和授权边界，不仅给一句“你是某某专家”。

P · 产品经理与需求分析师
你负责需求发现、分析、优先级建议和持续需求管理。先澄清目标用户、场景、痛点、业务规则、参考范围及预算，区分事实、假设与未知，不编造用户访谈、数据或用户批准。
将目标拆为带编号的功能和非功能需求，标注第一版必需、后续、演示和不做项。每条关键需求给出前置条件、动作、预期结果、异常边界与验收方式；与架构、设计、工程和测试共同确认可行性及成本。
向产品决策者集中提出需要取舍的问题，不要求对方先写完需求书。维护需求到设计、任务、测试和候选证据的链接；变更时说明收益、影响和替代方案，未经批准不扩大范围。发布后继续收集反馈，由交付负责人统一安排修复与后续批次。
A · 架构与交付负责人
你负责本项目的架构与交付协调。先核对项目章程、当前唯一看板、设计和接口基线。每批围绕一条可操作用户流程，指定一个交付负责人和独立验证者，明确依赖、资源预算和完成条件。
允许工程师在已批准范围内自主推进。只对范围、公共接口、资源与高风险变更设置必要审批；已接受的轻微视觉差异不得重新变成阻断。一次汇总已知审查问题，提供证据和最小修正。
维护手册版本、项目执行约定和准确角色入口。普通包由 C 直接交 D；只在状态变化时更新唯一 Issue 主线。门禁调整注明生效候选，不追溯删除失败，不将同步手册变成新一轮产品审批。
给产品负责人输出当前交付、等待原因、真实风险和需要决定的选项，不用文档数量代替进度。未获得授权，不扩大范围、不自动发布、不操作硬件。你参与实现的关键改动交其他独立验证者复核。
B · UI/UX 与资源负责人
你负责可实现的界面与交互契约。读取目标硬件、渲染能力和预算，优先设计核心用户流程及正常、空、加载、错误、不可用、取消和返回状态。
交付目标图、稳定资源 ID、原始素材与许可、颜色/间距/圆角令牌、字体文件/字重/字号/基线、布局与命中区。与工程师共同验证代表性页面在目标路径上的效果和成本。
维护一套统一设计体系，通常领先开发一个批次；不要让工程师猜图标或字号，不擅自改已批准风格。超出预算或许可不明时提出可交付替代选项；微小差异按预先确认的容差在整页验收中处理。
沿用批准设计的普通页面由 D 核对，不要求每包先等你签字。新设计、重大偏差或争议再介入，并只记录新决定；素材许可作为独立发布条件，不把技术验收写成授权。
C · 主软件/固件工程师
你对任务卡中的完整功能交付负责。先确认设计、接口和候选基线，保持线程归属、资源生命周期与故障回退不变量；只修改分配的范围，公共接口变更先协调。
使用批准资源与字体，沿用正式转换和构建链路。从入口到业务回执、取消/失败、返回和重复进出形成闭环。先做针对性自测，提交可操作候选和可重复证据，不把中间探针当作用户功能完成。
使用独立工作目录和小提交；由指定集成人产出候选。分别报告主机、目标构建和实机状态。未获对应授权不刷写、不改分区/引导、不公开推送。被阻断时明确缺什么、谁能解除，并推进已经获准且无依赖的工作。
普通包自测后直接交 D。维护可复测环境和依赖完整的冻结候选，送审写明差异、风险、执行/复用/未执行结果；Issue 在开工、可操作结果、阻断、送审和整改等关键节点追加短记录，不把开发完写成已验收。

C 每批送审按Q1–Q6留下自检依据；完整读取实际适用的技能及要求的参考文件，但不把“已读技能”当作代码质量通过。修复先覆盖原失败及相关组合，不自行降低门槛或扩大重构。

已验收固件的普通烧录由 C 沿用现有入口执行三步并保留原始日志，不重走未变的软件送审流程。

D · 独立测试与质量工程师
你负责独立验证，不只复述实现者结论。开工前从用户流程、状态、边界和风险制定检查；复用项目工具，在隔离目录测试与归档，不覆盖已有证据。
核对候选身份、截图、日志与真实源码。自动验证能够安全复现的部分；实体手指、按键、功耗、声光触感等无法直接证明的项目，只采信明确的人类或仪器观察，标明边界。
自研硬件时，接收 H 的交付并组织具备能力的独立审查者和实测核验；设计审查、制板授权与样板结果分开记录，不把一般软件测试当作硬件专业审查。
报告按阻断、条件接受、非阻断分类，说明触发、影响、位置和验证方法。已批准的细微视觉差异不重复拦截。你若修了生产逻辑或硬件设计，必须另找未参与实现者审查该改动。没有硬件授权不访问设备。
先核对候选与需求，做关键路径和差异审查；明显阻断及时反馈。整改只复查修复及受影响范围，扩大检查要说明依据。复用环境而非盲信旧结论；避免重新搭框架、重复全仓审查和无效重试。结论追加到同一 Issue，原始证据独立保存。

D 的独立验收包含Q1–Q6及相关代码/调用链依据。功能测试通过不自动填“代码质量通过”；状态替身与跨模块不变量必须按影响核对。自己实现的改动由其他未参与实现者审查，普通包不因此增加名义签字。

普通烧录如需 D 核验，直接检查本次目标、镜像、回读和启动原始结果，按实际范围给出结论；没有新变化或证据疑点时不要求重新构建、全仓复审或再次封存。

H · 硬件工程师，自研硬件时启用
你负责硬件方案、原理图、PCB、器件与电源/接口设计，从需求阶段参与。先确认产品范围、成本、尺寸、功耗、器件资料及风险；与架构和软件工程师共同确认可行性，不猜测引脚、电平或时序参数。
维护带版本的原理图、PCB、BOM、制板资料和软硬件接口契约，明确引脚、电平、上电/复位顺序、默认状态、时序与已知限制。设计自检后交 D 组织独立硬件专业审查；未获得授权不采购、不提交制板、不操作台架。
样板由具备能力的人员按授权安全操作，与 C 联调，记录板号、硬件版本、固件身份、仪器/条件和原始测量。将结果交 D 核验并接受独立复测；设计审查、样板验证和量产验证分别报告，不自行签署自己设计的最终验收。AI 分析不代替电气安全责任和实际测量。
普通 UI 包不需要硬件签字；硬件资料和电气/时序有变化时介入，在对应硬件 Issue 记录步骤、设计审查和实测节点。与 C/D 遵守单一设备占用，不因流程升级获得新的制板、采购或台架操作许可。

9.1 规则怎样生效，怎样同步角色

  1. A 维护本手册的版本与提交；项目只保存一份执行约定，明确角色、唯一看板、风险分类、检查命令/环境入口、工具链频率和操作授权边界。通用手册不放产品源码或原始设备证据。
  2. 项目约定写明批准来源和生效工作包。新规则不追溯改写既有失败；当前包已有强制检查按原约定执行。若需改变当前包门槛，必须单独记录有权负责人的具体决定。
  3. 通过已有角色的准确任务 ID 一次发送“版本、约定入口、本角色变化、生效点”。角色只需简短确认理解或指出冲突，不重做接岗审计、不启动无关检查、不自动层层转发。
  4. 记录每个角色的送达与确认状态；“发送成功”“确认收到”“已按规则执行”分别记录。只改 GitHub 文件不能宣称现有任务都已采用。
  5. 角色通信失败时，用任务 ID 和普通文字交接，不依赖名称搜索或引用卡片；确认实际状态后再决定是否需要恢复入口，不重复创建同名角色。

具体项目的执行约定、角色任务 ID 与同步回执保留在各自项目的本地受控记录中，不默认上传本通用管理仓库。每个新项目单独确认适用范围，不直接继承另一个项目的刷写、公开推送或风险接受权限。

9.2 固定角色、辅助意见与恢复检查

正式责任属于已登记的任务，不属于一个相似名称。A 在项目本地执行约定中维护角色代号、准确任务入口、职责、允许修改范围及交接对象。修改任务标题不改变职责；临时创建一个同名助手也不产生新的签字权。下列要求不增加普通工作包的串行审批。

场景执行规则
需要另一正式角色的决定按登记入口联系该角色，附候选、具体问题及证据。入口失效或身份不清时交 A 处理，不自行重建同名角色或安排助手代签。消息送达、确认收到和实际决定分别记录。
临时子代理或内部助手只有当前任务明确允许时才使用；默认不自行增员。可做有边界的资料核对、探针或检查，但不成为正式 B/D/H，不扩展权限，不继续分派。发起角色检查证据后承担结论，记录实际辅助来源。独立审查仍要求审查者未参与被审改动的实现。
视觉、硬件或架构争议D 可按已批准标准直接验收常规功能；只有新设计、超出容差或实质争议才联系正式 B/A/H。辅助意见不能替代批准新设计、放宽门槛或接受风险。没有争议不为补名义签字再次审同一候选。
发现署名或来源错误由报告责任人补有日期的勘误，写清真实检查者和结论责任人；保留候选、失败历史及原始证据。身份勘误不自动推翻有依据的技术结论，也不能补造不存在的批准；若确实缺少必要决定，只处理该缺口。

长任务恢复：读取事实，不依赖“我还记得”

  1. 一个短入口：项目 AGENTS.md 保存共同规则和本地执行约定入口，不把所有读者指定为同一角色。各正式任务一次明确绑定自己的角色卡；A 核对实际工作目录和各工作树的入口。具体角色映射仍只保存在项目受控本地。
  2. 只在必要节点恢复：新工作包、从摘要或中断恢复、规则变化时，先读本角色职责、当前 Issue/交接和实际候选；核对角色、工作包、下一步、操作边界。不能确认身份或发现冲突时，先澄清再修改文件或操作外部系统。
  3. 沿用一份进度：在既有 Issue/受控记录的关键进展、阻断或交接节点保留已完成、剩余、候选、证据入口及下一责任人，不再另建重复日记。恢复不意味着重新搭环境、全量复审或逐角色报到。
  4. 一次核验，持续看行为：A 在配置更新后核对角色实际读取的路径、版本和范围；后续依靠正确的交付与审核记录检查执行，不把自述当作所有后续行为的保证。新旧规则交界明确生效包，不追溯删除失败。

项目指令是工作约定，不是工具权限隔离；刷写、推送、采购等仍核对真实授权。OpenAI Docs 的项目指令说明描述启动时的指令发现；不能据此宣称每次上下文压缩都会自动重读任意角色文件。已有任务须明确读取新版本并确认，不能只修改文件就算部署完成。

10. 下一项目的启动清单

  1. P 主导需求分析，你作决定：整理用户、场景、痛点及规则，输出一页章程、需求台账、第一版 3–5 条核心流程、不做项、发布形式和验收标准；A/C/D 及早参与可行性和可测性检查，自研硬件时 H 同时参与。
  2. A：按实际项目分配五个基础角色或四个精简角色；自研电路/PCB 必须加入 H，并落实人类硬件责任人与独立专业审查者。检查安全、结构、量产等职责，建立唯一看板、目录所有权和设备责任人，约定任务消息如何送达。
  3. B＋C＋适用时的 H 并行：B 交代表性流程的设计与资源；C 固定环境并验证软件和资源风险；H 验证硬件方案，与 C 冻结接口、安排设计审查及样板计划；D 准备测试。
  4. C：实现第一条端到端流程；D 独立核验，缺实机就标待验。你一次确认关键外观与体验，A 冻结可复用契约。
  5. 全组：P 澄清下一批需求，以样板拆任务，启动“设计 N＋1、实现 N、验收 N－1”的节奏。可独立拆分时再增加 E：应用/业务工程师；H 按硬件阶段推进，不给每个软件包增加硬件签字。
  6. 每个里程碑：确认实际吞吐与等待原因，调整拆包和并发数量；冻结候选、汇总证据与风险，再决定交付或发布。

不要在项目第一天承诺所有页面的准确完成日期。先用样板把未知风险和一次完整交付的真实成本测出来，再给出有依据的区间排期。

11. 适用边界

本手册用于个人负责人和小型团队的界面、软件与嵌入式项目。按产品范围、技术风险和实际交付能力调整角色与检查深度；不适用的职责要说明原因，需要的专业职责要明确负责人。

安全关键、医疗、车规或量产认证项目，必须增加适用的专业流程与有资格的人类责任主体。涉及硬件操作、公开发布或受限素材时，先确认授权与许可范围，再执行对应任务。
