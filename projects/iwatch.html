iwatch：开发、验收与记录执行约定

2026-09-24 · IW-PROCESS-20260924-1 · 对应通用手册 v1.3

批准来源：产品负责人要求更新私有管理手册、同步现有角色，并记录开发过程与步骤。通用原则见分级与增量验收；本页只补 iwatch 的执行边界，不复制产品设计与测试证据。

1. 从哪里生效，不改变什么

  • 普通功能继续由 C 直接交 D；不再等待 A 预签。D 按批准设计核对，只有新设计、实质偏差或争议找 B；纯 UI 改动不要求 H 签字。
  • 送达本约定时已开始的工作包，包括当前 V00 五页整改，保持原有必跑检查和验收条件。可以立即减少重复准备、复用经核验的无影响证据并记录关键步骤，但不能删除失败、降低原有门槛或自动通过。
  • 下表的开发/里程碑构建频率用于送达后新开工的普通工作包。C 开工时写明工作包与本约定 ID，D 检查风险是否适用；若与明确的项目硬约束冲突，A 先解决冲突，未解决部分按原要求执行。
  • 控制中心已有阶段验收范围不因这次流程升级重新签字；当前待整改功能仍须独立复核。#8、#10、D15 等独立问题保持各自范围，不由本页判定关闭。
  • 不改变 GUI 线程归属、输入仲裁、资源所有权、390×450 设计基线或已批准的视觉容差。受限素材的发布限制独立保留。

本次授权仅覆盖管理文档、流程同步及约定范围内的过程记录。不是刷 COM9、读取 COM10、操作 J-Link、改分区、推送产品代码、关闭产品 Issue 或发布素材的授权。硬件操作仍核对具体目标与既有许可。

3. 一个候选，一个复测入口

  1. C 维护经过验证的干净 SDK、补丁 SDK、工具链和短路径环境；沿用现有测试脚本。送审时包含测试所需文件和资源定位，不只打包链接固件所需的源码。
  2. 候选使用提交加资源清单，或包含未提交输入的不可变快照；仅有当前 Git HEAD 不足以标识未提交候选。D 不用默认工作树旧代码冒充候选，也不修改 C 的原始归档。
  3. 最小交接内容：Issue/工作包、候选身份、相对上轮差异、设计/范围、实际检查与证据、已知限制及本轮请求验证项。信息已有入口时只链接，不重复重写。
  4. 复用结果须说明相关源码、资源、SDK/工具链、配置、夹具和板级条件仍适用。受影响、存疑或曾失败的检查重新执行；分别标注本轮执行、有依据复用、未执行和阻断。
  5. 环境排障约 10–15 分钟先给事实反馈，不无限重试、不绕过 clean-base 检查。可继续的代码/截图检查独立推进，环境阻断不冒充产品通过。

4. 当前在 Issue #16 续写关键过程

当前 D14/V00 相关工作沿用 Issue #16：[D14] 蜂窝桌面与应用转场。每个子工作包以固定标题/编号区分；已有编号沿用，真正独立的新功能才按需开新 Issue。不要为采用本模板复制现有功能 Issue，也不要把所有后续功能无差别塞进 #16。

C：开工列 3–7 项步骤；有首个可操作结果、阻断或关键决定时追加短记录；开发完记“待 D 验收”，附候选和自测证据。D：独立验收与整改复验结论追加在同一工作包线程/Issue，C 不代签 D 的通过。

评论格式直接用手册的开发与验收模板。没有状态变化不重复评论；已有结果补录时注明实际补录时间和证据日期。Issue 表单可从模板复制；本次未安装或修改产品仓库的 Issue 配置。

iwatch 仓库公开：只发脱敏摘要、允许公开的提交和证据 ID；受限图标/截图及固件、完整设备日志、私有角色 ID 和本页内容不直接贴到公开 Issue。受控本地证据保留唯一入口供验收者读取。无对应内容权限时先记录在受控台账，不擅自公开。

本页不改变产品 Issue 的关闭权限。现有父阶段 Issue 不因某一子页面通过而关闭；是否具备关闭条件由原范围、D 结论和必要实机结果共同决定。技术状态、素材许可和公开发布分别管理。
